# Experiment tracking with MLflow

Every pipeline stage logs one MLflow run. Each run records its parameters (the relevant
config section), metrics, figures, tables and tags. Runs are stored in a local SQLite file
(`mlflow.db`) and their artifacts in `mlruns/`. Both are git-ignored, because they are
regenerated by `python -m equipoise all` or `dvc repro`.

## Open the UI

```bash
mlflow ui --backend-store-uri sqlite:///mlflow.db
```

Then browse to http://localhost:5000. On Windows, run this from the repository root with the
virtual environment activated.

## How runs are organised

| Experiment | Stage | What to look at |
|---|---|---|
| `equipoise-m1-preprocess` | missing data, CST harmonization, outliers | arm differences under complete-case / KNN / MICE |
| `equipoise-m2-stats` | Table 1, replication, tests | replication vs published, ANOVA / Welch / chi-square |
| `equipoise-m3-represent` | PCA/SVD, clustering, Apriori | scree plot, silhouette scan, cluster effects |
| `equipoise-m4-search` | feature search arena | convergence plot; one run per algorithm and seed |
| `equipoise-m5-supervised` | regression / classification / count models | one child run per model with CV and held-out metrics |
| `equipoise-m6-causal` | CATE learners, policy value, bundle | semi-synthetic PEHE, policy values, chosen learner |
| `equipoise-m7-longitudinal` | trajectories, ARIMA, HMM, early response | early-response gain over baseline-only |
| `equipoise-m8-decision` | cost, break-even, fuzzy, expert system | population summary, Newton vs brentq check |
| `equipoise-m9-explain` | SHAP, subgroups | SHAP importance, subgroup calibration |
| `equipoise-m11-monitor` | Evidently drift | drift share, HTML report artifact |

Synthetic-data runs (`--synthetic`) go to the same experiments with the tag
`data_source = synthetic`. Filter them out with `tags.data_source = "real"` in the search box.

## Reading a run

- **Parameters**: the flattened config section the stage used (for example
  `causal.causal_forest.min_samples_leaf`). Comparing two runs shows exactly what changed.
- **Metrics**: the same numbers that are written to `reports/metrics/<module>_<stage>.json`.
  DVC tracks these too, so `dvc metrics diff` and the MLflow compare view agree.
- **Artifacts**: `figures/` and `tables/` hold the exact files in `reports/`. On real-data runs M6 also logs
  the model bundle.
- **Tags**: `git_commit` (the code version), `data_version` (hash of the input table),
  `data_source` (real / synthetic). A run can always be traced back to its code and data.

To compare runs, select two or more in an experiment and click **Compare**. Then plot a
metric against a parameter (for example M5 RMSE per model, or M4 best objective per
algorithm).

## Model registry

The M6 stage registers the bundle as **`equipoise-cate`**, creating a new version on each
real-data run. The version the API should serve is marked with the alias **`champion`**:

```bash
python -m equipoise promote              # alias the newest version as champion
python -m equipoise promote --version 7  # or pick a version explicitly
```

`promote` also tags the version with the learner name and the training-data hash of the
local bundle. In the UI, open **Models → equipoise-cate** to see the versions, their source
runs and which one carries `champion`. MLflow 3 uses aliases in place of the old
Staging/Production stages.
